# 知识库建设原则

本文是 bytedepth 知识库（`docs/`）的建设宪法，适用于新增、修改、迁移或删除知识库文档。所有文档变更必须先对照本文。`docs/README.md` 是知识库入口，其维护规则是本文的精简索引。

## 目标

**需要知识时找得到、找到的必准确、准确的能复用。** 三者缺一不可：找不到的知识等于不存在；找到但过时的知识比没有更糟；准确但无法复用的知识只是记录。

在 AI 辅助开发时代，知识库不仅给人读，也是 AI 代理的上下文。过时或不准确的文档会被模型当作事实、放大为错误假设（Karpathy 观察到“模型会代你做错误假设，然后不假思索地执行”）；因此准确性在此比传统文档更高一个量级，且约束应尽量可校验，让“文档即测试”的思路得以落地。

## 一、可发现性

让知识在需要时能被定位，而不是靠记忆或翻找。

1. **单一总入口。** `docs/README.md` 的“从这里开始”列表是唯一入口，覆盖所有主题；每项是一个动词短语加链接（“修改 X：读 Y”），不是一个章节标题。
2. **主题单一权威入口。** 每个主题只有一个权威文档；其他文档遇到该主题用链接指向它，不复制内容。避免两个文档描述同一事实。
3. **命名即索引。** 文件名和标题用业务或技术名词（`authentication`、`rbac`），不用日期、需求编号或“v2”后缀；需要历史时在文档内部用日期，不用日期当文件名。
4. **双向链接。** 下层文档回链上层和相邻主题；上层文档的延伸阅读指向下层。读者从任一文档进入都能导航到相关内容。
5. **导航随内容增减。** 新增文档必须同步加入入口导航；删除文档必须同步移除导航。无导航的文档等于失联。

## 二、渐进式披露

按读者当下需要展开信息，不一次性倾倒全部细节。

1. **入口层只放结论与链接。** `docs/README.md` 只放稳定结论、一行概要和链接，不展开细节。
2. **主题层放摘要、约束与配置。** 主题文档（如 `security/authentication.md`）先写结论和约束，再放关键配置与口径，最后链接到源码位置；不堆砌实现过程、进度或会话记录。
3. **代码是最终真相。** 文档指向关键文件和类名，不逐行复述源码；源码变更后文档指向仍需有效。
4. **链接而非复制。** 同一信息只在一个权威位置定义，其余位置链接。不以重复粘贴换取“完整”——重复会制造多个需要同步的真相源。

## 三、准确性

只写可被当前代码验证的内容；无法验证的不进知识库。

1. **以代码为准。** 文档以当前代码和唯一操作手册为真；无法验证的历史说明、未落地的设计不迁入。
2. **迁入前验证。** 涉及代码行为、配置值、接口契约的事实，迁入前必须对照源码核实，不能只依据设计文档或会话记忆。
3. **偏离即标注。** 实现与历史设计文档不一致时，以代码为准，在文档写明实际行为而非设计意图。
4. **过期即更新或删除。** 文档与代码不一致时先核实当前业务规则；确认后同步修改代码或文档，不保留两个真相来源。
5. **可校验优先。** 涉及配置值、契约或口径的约束尽量给出可核实的锚点（文件路径、类名、迁移版本号），让人和工具都能据此校验文档与代码一致；约束越具体、越可被脚本或检索核对，越不容易漂移。

## 四、稳定性

只沉淀影响后续改动的稳定决策；过程性内容不进知识库。

1. **只迁入有后续约束力的内容。** 架构契约、组件契约、口径约定、故障复盘、不可逆决策。已固化在代码且无后续约束力的一次性决策不迁入。
2. **不迁入过程性内容。** 需求计划、实现进度、会话记录、临时排查日志、逐次实现过程，留在需求管理或会话中，不进知识库。
3. **决策标注性质。** 稳定决策直接陈述为约束；可能演进的决策注明是方向性草案，不写成不可逾越的规范。
4. **删除也是维护。** 过时或已被其他文档覆盖的文档应及时删除，不要累积成无人维护的归档。

## 五、分层组织

文档边界与架构关注点对齐，不按时间或需求分目录。

1. **按关注点分目录。** `architecture/` 放模块边界与设计约束，`engineering/` 放可复用模式与故障经验，`security/` 放安全决策，`releases/` 放版本与发布，`agent-guides/` 放任务操作指南。
2. **不按需求或日期归档。** 废弃以需求编号或日期命名的归档目录；有价值的内容迁入对应关注点目录，无价值的删除。
3. **跨层决策归位。** 跨模块的决策放在描述边界的文档（如 `architecture/overview.md`），不放单个模块的文档。

## 六、维护性

让文档随代码演进，且单点修改不需要触动多处。

1. **随代码一并提交。** 架构决策、公共组件契约、故障复盘必须随相关代码的 PR 提交，不事后补录。
2. **工具目录不入库。** `.omc/`、`.superpowers/`、`.claude/` 等工具运行目录只保存本机状态，永不作为项目知识库。
3. **低摩擦更新。** 文档结构应让单点修改（如某项配置变更）只改动一个位置；若同一事实散落多处，说明违反了“链接而非复制”，应合并。

## 自检清单

变更知识库前逐项确认：

- [ ] 新增文档是否已加入 `docs/README.md` 导航？
- [ ] 内容是否已对照当前代码核实，而非依据设计文档或记忆？
- [ ] 是否只写了影响后续改动的稳定决策，未混入过程或进度？
- [ ] 同一信息是否只在一个权威位置定义，其余用链接？
- [ ] 读者能否从入口导航到本文档，再从本文档导航到相关主题与源码？

## 方法论依据

本原则综合以下来源：Karpathy 对 LLM 编码陷阱的观察（错误假设被放大、简洁优先、改动精准、目标驱动可验证——知识库作为 AI 上下文时这些风险被进一步放大）；Diátaxis 文档分类法（按学习、任务、参考、理解四种模式组织，不混淆文档类型）；Docs as Code（文档与代码同生命周期、随 PR 提交与审查）；以及单一真相源、渐进式披露与认知负荷等经典信息架构实践。
