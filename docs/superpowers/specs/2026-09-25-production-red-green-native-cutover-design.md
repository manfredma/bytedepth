# 生产 native 红绿切换设计

## 目标

在 175 多服务宿主机上，将 bytedepth 从当前 Docker 运行时迁移为 native 全栈运行时，并保持可验证、可回退的生产发布流程：先部署绿环境，完成全栈健康检查和只读回归，再在短暂停机窗口内完成最终数据同步和 Nginx 切流。

## 运行拓扑

蓝环境保留当前 Docker 应用、MySQL、Redis、Meilisearch 和共享 Nginx。绿环境使用独立资源：

| 资源 | 绿环境约束 |
| --- | --- |
| 根目录 | `/data/bytedepth-native-production` |
| MySQL | 13306，独立数据目录和 native unit |
| Redis | 16379，独立数据目录和 native unit |
| Meilisearch | 17700，独立数据目录和 native unit |
| 应用 | 18080，systemd 管理的不可变 JAR |
| edge | 18081，只服务 bytedepth 绿环境 |
| 公网入口 | 共享 Nginx，仅 reload bytedepth upstream |

所有新建项目文件、配置、发布制品和迁移状态由 `ubuntu` 持有；服务账号只通过服务组获得数据目录所需写权限。其他项目的端口、容器、数据目录和 Nginx 路由不在本设计范围内。

## 发布状态机

```text
检查蓝环境与共享边界
  -> 准备绿目录、unit、配置和制品
  -> 初始复制数据（蓝环境继续服务）
  -> 启动绿中间件和应用
  -> 绿环境本机健康、SHA、只读回归
  -> 短暂停机：停止蓝应用并完成最终同步
  -> 启动绿全栈并重复健康检查
  -> nginx -t -> reload bytedepth upstream
  -> 公网 SNI、版本、页面和日志验收
  -> 保留蓝环境，验收通过后再显式清理
```

任何阶段失败都停止后续步骤。切流前失败只停止并清理未接管的绿资源；切流后失败先恢复 blue upstream，再确认蓝应用和数据状态，不能无条件双向切换已发生写入的数据。

## 数据一致性

初始复制和最终同步必须分别记录源、目标、时间、版本和校验结果：

- MySQL 使用受资源约束的事务一致性导出/导入流程，禁止无界 dump、将密码放入命令行或覆盖非目标库。
- Redis 使用受控快照复制，并校验密码、RDB 完整性和目标实例状态。
- Meilisearch 使用版本化 snapshot，等待导入任务完成后再启动应用。
- 图片使用显式源目录和目标目录的校验复制；不对整个 `/data` 做递归删除或覆盖。

短暂停机窗口内先停止蓝应用，阻止新的业务写入，再完成最终同步、启动绿应用和验证。切流前不删除蓝数据；切流后回退必须依据是否已有绿环境写入决定，若已有写入，先停写并执行受控数据回退，不能只切 Nginx。

## 脚本边界

- 本机仍只调用 `deploy/deploy-production-remote.sh vX.Y.Z`，不调用生产内部脚本，不执行本机 sudo。
- 175 内部脚本负责绿环境安装、迁移锁、状态文件、systemd 启停和 Nginx reload。
- 生产部署锁必须覆盖初始复制、最终同步和切流，避免同机发布并发。
- 共享 Nginx 只能执行配置测试和 reload；不重启、停止或重建 Nginx，也不触碰其他项目配置。
- Docker 清理是切流并完成生产验收后的单独显式阶段，不能由失败回退路径自动执行。

## 验证与测试

- 为迁移状态机、端口/目录边界、服务前缀、数据复制失败、Nginx 配置和回退顺序补充脚本契约测试。
- staging 继续使用 129 独立 native 环境完成全部集成测试和 E2E；生产只执行发布脚本的只读验收，不把 175 当成测试环境。
- 正式 Tag 创建前，两份 staging evidence 的完整 SHA 必须等于合并后的 `main` HEAD；生产只接受新的 annotated SemVer Tag。
