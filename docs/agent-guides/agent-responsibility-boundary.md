# 人与 Agent 的职责边界

本文是 bytedepth 中人与编程 Agent 协作的职责边界。它约束交付方式，不替代具体模块的架构、测试或发布规范；相关主题应回到对应的唯一权威文档。

## 核心结论

Agent 负责把需求变成可验证的交付结果，并在交给项目所有者前完成自测、问题定位和闭环。项目所有者负责目标、取舍和最终业务验收，不负责替 Agent 发现必现的构建、启动、登录、接口、交互或部署缺陷。

“请项目所有者先试一下，再根据反馈修复”不能作为开发完成或 staging 可验收的依据，除非该步骤本身就是需要真实用户判断的业务、视觉或体验验收。

## 默认交付终点与授权范围

这是本仓库的 Agent 开发与交付规则。CI/CD 是构建、部署和验证的执行工具，不是 Agent 开发流程的授权来源；Agent 负责调用工具、跟踪结果和闭环，不能把交付责任转交给 CI/CD。

用户提出功能、修复、文档或格式化任务，即默认授权 Agent 在本任务范围内提交、推送分支、创建或更新 PR，并推进 staging 部署与验证；无需为这些常规交付步骤逐次请求指令。设计取舍仍按项目规则确认，交付授权不扩大需求范围，也不授权操作无关项目。

- **默认（需要人工验收）**：完成实现、回归测试、格式化、本地质量门禁、变更记录及版本准备后，提交并推送任务分支、创建或更新 PR，推进 staging 部署，检查健康状态、日志与集成/E2E 证据。确认该候选已具备验收条件后，才停下请求人工验收。停点是“staging 已就绪，等待业务验收”，不是“本地测试通过”“等待提交指令”或“等待 staging 部署指令”。
- **明确免人工验收**：用户对本任务明确说“不需要人工验收”“无需我验收，直接上线”等，视为对该任务在全部门禁通过后的上线授权。Agent 仍先完成 staging 部署与验证，然后使用既有 CI/CD 机制完成验收状态登记、同一 SHA 的合并与同一不可变制品的生产发布，持续跟踪到生产验证成功的终态，不再等待用户重复确认。授权依据必须记录为用户的免验收指令，不能伪称用户已查看或手工验收；该授权不自动延续到其他任务。
- **明确限制范围**：用户要求“仅分析”“只在本地修改”“不要提交”“不要部署”等时，以该限制为交付终点，并明确说明尚未执行的步骤。“继续”或没有回复不等于免人工验收授权。
- **真实阻塞**：缺少凭证或权限、平台不可用、未解决的门禁失败、状态不确定，或确实需要用户作设计取舍时，可以提前停下；报告具体阻塞、已尝试的动作、可复核证据、尚未执行的步骤和需要用户提供的最小信息。具备条件却等待下一条常规交付指令，不属于阻塞。

免人工验收只免除等待人工确认，不免除质量门禁、staging 集成/E2E、健康与日志检查、SHA 与制品一致性检查，也不允许绕过 CI/CD、直接操作主机或伪造验收证据。

进度与完成状态按证据命名：仅本地通过是“开发与本地验证完成”；部署仍在运行是“staging 部署中”；部署及自测通过才是“staging 待人工验收”；明确免验收并完成生产验证才是“已上线”。没有部署回执不能把任务称为“已交付”。

防复发检查：`bash scripts/test-agent-delivery-workflow.sh` 检查默认停点、常规交付授权、免人工验收分支、阻塞例外、任务追踪、主线优先与诊断规则及入口链接；该检查由本地质量入口执行，不调用 CI/CD 或远程环境。它只检查规则与导航是否保留，不证明 Agent 已实际遵守，执行效果需由任务记录和结果证据核对。

## 任务追踪与范围变更

多阶段、跨会话或反复失败的任务，由 Agent 维护一份可交接的任务清单；单步且可当场验证的修改无需另建清单。沿用已有 Issue、PR 或持久化任务记录，并在交接中给出唯一位置；具体进度和排查日志不写入项目知识库。

每项需求保留稳定编号，记录用户目标、可观察的验收条件、当前状态、证据位置与适用的提交/环境，以及未完成项或阻塞。任务级记录明确本轮范围、非目标和交付终点；组件实现、部署结果和业务验收分别按证据更新，局部完成不能关闭整项需求。

- **开始或恢复**：接手任务、恢复会话或上下文压缩后，先读取清单和最新用户指令，核对当前分支、提交与相关环境事实，再执行下一步；记录冲突或已失效的证据。
- **范围变化**：将新要求标为追加本轮、替换旧要求或延后，并同步更新验收条件、撤销失效步骤。意图明确时直接记录并执行；只有影响目标、成本或交付终点且无法判断时，才请用户作取舍，同时继续不受影响的工作。
- **收尾或交接**：逐项核对仍有效的需求和证据，列出剩余工作、阻塞及下一步；只有全部验收条件满足，或用户明确撤销该项要求，才能关闭对应项。

反复失败时，按[诊断与重试](../engineering/gotchas.md#诊断与重试)维护调查记录，并将结论关联到任务清单；通用故障规则仍归入对应主题的权威文档。

## 主线优先与 backlog

移动化交付暴露过一次范围失控：为交付 APK 持续扩展构建平台配套，把默认运行时选型当作必须安装的前提，并混淆编译与模拟器验证的依赖，导致配套工作长期占据主线。根因是没有逐项证明这些工作与用户验收的依赖关系，也没有及时延后次要问题；范围控制由 Agent 负责，不能依赖用户反复提醒。

开始、恢复任务或遇到新问题时，在已有任务清单中执行以下判断，无需新建流程或管理系统：

1. **明确主线**：从用户可观察的验收结果倒推当前必要步骤，写明下一步及通过条件。进度围绕可交付结果报告，不能用配套代码量或局部测试数量代替。
2. **证明阻塞**：每项阻塞写清“阻止哪一步、实际证据、最小解除动作”。未知项先安排最小验证，不直接宣称阻塞。编译、签名、安装、模拟器验证分别识别依赖；某个验证步骤缺条件，不自动等于无法编译。
3. **复用环境**：优先验证现有运行时和工具链，核对当前版本的官方兼容要求，并执行相关真实构建或验证。官方默认版本、最低版本和唯一可用版本含义不同；仅因默认推荐不同，不能要求安装第二套运行时。出现可复现不兼容后，再选择满足要求的最小调整。
4. **收紧改动**：只解决当前步骤的直接缺项及执行该步骤必需的安全、正确性问题。配套方案应说明它解除哪个已确认阻塞；已投入的时间、已批准的方案或局部测试通过都不能证明剩余工作仍属主线。
5. **延后次要项**：通用化、额外可观测性、扩大兼容矩阵及非必要重构进入 backlog。每项记录问题、影响、延后理由、重新启动条件和验收条件；任务专属项留在原任务记录，跨任务技术债归入[技术债清单](../engineering/technical-debt.md)，不复制两份。主流程跑通后再处理 backlog，或在新证据证明其阻塞当前交付时提升优先级。

本规则用于缩小需求范围，不降低既有测试、签名、权限、发布和人工验收要求。已确认会破坏当前执行安全或正确性的缺陷，必须在使用相应路径前修复；必需门禁中的失败、未解释告警和证据缺失不能以 backlog 名义放行。扩展成本、目标或交付终点的取舍按[任务追踪与范围变更](#任务追踪与范围变更)处理，其余日常优先级由 Agent 自行判断并执行。

## Agent 的交付责任

Agent 在请求项目所有者验收前，必须完成与改动风险匹配的验证，并保留可复现证据：

- 先阅读本项目的 `AGENTS.md`、知识库入口和相关操作指南，遵守分支、worktree、测试、staging 与发布边界。
- 对代码或配置改动补齐相应的单元测试、契约测试或静态检查；业务逻辑分支按项目覆盖率门禁执行。
- 对登录、OAuth、表单、接口、部署等关键链路，至少走通一次真实的成功路径，并检查失败路径、重定向、会话和错误日志。
- 对界面改动完成自我视觉检查和受影响设备/断点检查；项目所有者验收用于确认产品判断，不用于发现明显错位、空白页、按钮不可用或必现错误。
- 对失败结果先定位根因，再修复并重新验证；不得把未解释的 `403`、`401`、重定向循环、启动失败或 WARNING 转交给项目所有者作为“验收反馈”。
- staging 部署后先由 Agent 完成部署健康检查、集成测试和 E2E；证据不足时状态只能是“未就绪”，不能请求项目所有者验收。
- 记录会影响后续任务的根因、规则和自动化检查；同类问题不得只依赖 Agent 的会话记忆。

## 项目所有者的验收责任

项目所有者的验收重点是 Agent 无法替代的判断：

- 需求是否满足，业务语义和产品取舍是否正确。
- 页面视觉、文案、信息层级和交互体验是否符合预期。
- 真实使用场景下是否接受已知的产品权衡。
- staging 候选是否允许进入合并和发布流程。

项目所有者发现问题时，Agent 应把它当作交付质量信号：先判断问题属于漏测、根因未闭环还是新的产品决策，再分别补验证、修复或请求明确取舍。不能要求项目所有者反复充当 E2E 测试人员。

## 请求验收的最低证据

发起 staging 验收前，交付说明至少应包含：

1. 候选分支或提交的完整 SHA。
2. 本地质量门禁、单元测试和静态检查结果。
3. staging 部署结果、服务健康状态和日志检查结果。
4. 关键用户链路的集成/E2E 结果及失败项处理结论。
5. 已知限制，以及需要项目所有者做产品判断的具体问题。

如果第 2–4 项缺失，或存在未解释的失败、WARNING、必现缺陷，不能声称“已完成”或“可以验收”。

## 验证访问的统计边界

Agent 在回读正文、浏览页面和验收站内链接前，按[无痕阅读与验证流量](../engineering/view-log-and-analytics.md#无痕阅读与验证流量)标记请求；浏览器从带验证参数的入口访问，脚本和 E2E 使用显式请求头，不能假设工具天然可被 UA 识别。长任务检查模式有效期，验证后退出；对外交付干净文章 URL。统计专项测试在隔离上下文验证普通请求仍计数，不能用被过滤的默认请求证明计数正确。

## 与其他规范的关系

- 发布时序、staging 唯一验收环境和 evidence 约束以 [统一发布流程](../engineering/unified-release-pipeline.md) 与 [Git 工作流](../engineering/git-workflow.md) 为准。
- PR opened/synchronize 后，release-platform 以 PR head SHA 创建候选并执行 QUALITY/BUILD/staging；Agent 负责核对候选 SHA、读取 flow/stages/logs/evidence，并在 staging 验收通过后合并同一个 SHA。合并后的 `main` SHA 校验通过后，Host Agent 才能提升同一 artifact 到 production。没有平台回执时只能交接触发参数，不能声称已触发或已验收。
- 测试边界以 [Maven 与测试指南](maven.md) 及 [staging 集成测试边界 ADR](../architecture/decisions/0002-staging-integration-test-boundary.md) 为准。
- 故障沉淀遵循 [知识库建设原则](../knowledge-base-principles.md)；必须同时记录可验证根因、可执行规则和可重复检查。
