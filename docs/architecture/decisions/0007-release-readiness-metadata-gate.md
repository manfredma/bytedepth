# ADR-0007: 将发布变更记录前置为 staging 硬门禁

- **状态**: Proposed
- **日期**: 2026-09-15
- **决策者**: 项目所有者

## 上下文

现有发布文档要求功能改动在 PR 阶段写入 `CHANGELOG.md` 的 `Unreleased`，但文件顶部的描述容易被理解为只记录正式 Tag。质量门禁、staging 部署和合并入口也没有执行这项要求，导致候选可以在没有用户可见变更记录的情况下进入 staging，直到创建正式版本时才暴露问题。

发布候选必须在首次 staging 部署前冻结代码、测试和用户可见变更说明；任何提交变化都必须重新验证，不能复用旧 SHA 的 staging evidence。

## 决策

将 `CHANGELOG.md` 的 `Unreleased` 变更记录定义为运行时改动进入 staging 的硬前置，并由同一个可重复的检查脚本在本地质量、CI、staging 部署、合并前和正式发布入口执行。检查必须 fail-closed：缺少标题、分类或非空条目时直接失败；纯文档维护改动不触发该检查。

选择单一共享检查脚本，而不是在多个入口复制正则逻辑，以保证规则和错误信息一致。保留 `prepare-release.sh` 对正式版本标题的独立检查，因为 `Unreleased` 门禁和正式 Tag 门禁属于不同阶段。

放弃只修改文档的做法，因为文档约定已被本次遗漏证明不足；放弃只在 `prepare-release.sh` 检查的做法，因为发现时点过晚且候选已经完成 staging 验收。

## 后果

**正向**

- 缺少 `Unreleased` 的运行时代码不能通过规定的本地、CI 或 staging 流程。
- 规则只有一个实现，所有入口和契约测试共享同一语义。
- 候选的变更记录在 staging 前冻结，SHA 变化会自然触发重新部署和重新生成 evidence。

**负向**

- 每个用户可见或运行时改动都必须同步维护 Changelog。
- 多个入口执行同一检查会增加少量流程时间和维护成本。
- 纯文档改动需要可靠地定义和测试豁免边界。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| `CHANGELOG.md` 是本项目用户可见发布说明的唯一来源 | 发布说明改由外部系统生成或拆分为多个产品说明源 |
| `origin/main` 可作为候选变更范围的稳定基线 | staging 部署时无法取得对应远程 main 或采用其他集成分支 |
| 规定的本地、CI、staging 和 release 入口都会持续使用共享检查脚本 | 出现绕过这些入口的受控发布系统 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 变更记录需要结构化字段、审批或多语言发布管理 | 评估独立发布元数据格式并以新 ADR 替代本决策 |
| 入口增加到无法保证共享脚本被调用 | 将检查提升为统一发布控制器的单一状态转换，不再允许脚本各自推进 |
