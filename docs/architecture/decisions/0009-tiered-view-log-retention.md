# ADR-0009: 分层保留访问统计并由 Spring 定时归档

- **状态**: Accepted
- **日期**: 2026-09-18
- **决策者**: 项目所有者

## 上下文

`post_view_log` 和 `page_view_log` 目前同时承担访问明细和统计分析数据源的职责。访问明细包含 IP、User-Agent、Referer、GeoIP 和阅读进度等高基数字段，长期保留会持续扩大 MySQL 表空间；直接删除历史行又会丢失长期趋势和国家分布。

当前系统已经启用 Spring Scheduling，并由 `RedisStatsService` 使用 `@Scheduled` 刷新页面热度。生产和 staging 均为单应用实例，但未来可能扩展为多个应用实例，因此归档任务需要数据库级互斥。现有 `post_view_log` 还包含自增主键和 `visit_token` 唯一索引，不适合直接按 `visited_at` 改造成时间分区表；MySQL 要求分区字段包含在所有唯一键中。

## 决策

采用“近 7 天原始明细 + 永久分层聚合”的数据生命周期：

1. 原始明细只保留近 7 天，文章访问和普通页面访问均适用。
2. 文章/页面 PV 以小时、对象维度永久保存，用于排名和趋势。
3. 国家 × 文章/页面 PV 以天、对象维度永久保存。当前后台没有国家小时趋势，因此不为所有国家生成小时级数据。
4. 使用 Spring `@Scheduled` + 独立 `TaskScheduler` 执行归档，不新增 Quartz、Spring Batch 或 ShedLock 依赖。
5. 使用 MySQL named lock 保证多实例下只有一个归档任务运行；每个小时段使用独立事务完成聚合、删除明细和推进归档状态。
6. 使用归档小时状态表处理重试和迟到数据。一个小时段首次归档时写入精确聚合；已归档小时若又出现迟到明细，则只增量合并迟到记录，再删除这些记录。
7. 低峰期按来源级持久化累计删除量阈值执行 `OPTIMIZE TABLE`，仅在成功后清零计数，不在每个归档小时后重建大表。

放弃按时间分区原始明细表：现有唯一键约束会迫使主键和访问令牌定位模型一起重构，收益不足以抵消迁移风险。放弃访问写入时直接更新所有汇总表：它会把异步事件失败、重复消费、访问令牌幂等和历史回填耦合到写入链路。

## 后果

**正向**

- 访问明细空间被限制在约 7 天，IP、User-Agent、Referer 等隐私和高基数数据不会永久增长。
- 文章/页面趋势保持小时级，国家排名和分布保持历史可查询。
- 归档任务可追赶历史积压；事务和小时状态使中断重试不会重复计数。
- 不引入新的任务框架，符合现有 Spring Boot 结构和单机部署模型。

**负向**

- 统计 SQL 需要同时读取聚合表和最近明细，并合并两段结果。
- 历史国家统计的最小粒度是天，不支持按国家按小时回溯。
- `OPTIMIZE TABLE` 是低峰期维护操作，仍可能产生 I/O 和元数据锁等待。
- 旧版本代码在归档删除开始后不能作为安全回滚版本，因为旧代码只读取原始明细。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| 访问事件的 `visited_at` 来自在线请求时间，迟到事件只会是少量异常 | 出现大量写入已归档小时的事件，改为记录接收时间并增加迟到补偿扫描 |
| 当前分析需求只要求文章/页面趋势小时级，国家维度按天足够 | 产品出现国家小时趋势需求，单独增加可控国家集合的小时汇总 |
| 单站点的对象数量和国家基数符合行数公式的容量预算 | 聚合表或索引超过预算，先降低维度或增加日/月级降采样，再考虑分析型存储 |
| MySQL `innodb_file_per_table` 保持启用 | 表空间文件删除后未缩小，检查实例配置并改用受控表重建方案 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 小时聚合年增长超过容量预算的 2 倍 | 保留最近一年小时级，旧数据降为日级；先补迁移和查询兼容性测试 |
| 归档延迟超过 24 小时或连续失败 | 停止删除阶段，仅允许聚合回填，排查数据库锁、空间和任务错误 |
| 归档后统计与原始明细对账不一致 | 暂停表空间维护，保留明细，使用归档状态和重算任务修复后再继续 |
| 需要多实例且 named lock 不能满足调度治理 | 评估 ShedLock 或独立部署 worker，但需先更新 ADR |
