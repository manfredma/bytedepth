# ADR-0008: 统一生产远程部署入口与 staging 预览路由

- **状态**: Proposed
- **日期**: 2026-09-16
- **决策者**: 项目所有者

## 上下文

生产部署脚本依赖生产主机上的 `/etc/bytedepth-deploy.conf`、Docker、共享 Maven 缓存和 root 权限。本机直接执行该脚本会产生误导性的 sudo 错误；SSH 前台会话中断时，脱离会话的远程部署又可能继续执行，造成任务状态不透明。

同时，staging 域名当前对公网直接提供内容。项目希望普通公网流量进入生产，但保留团队通过 staging 做验收的能力。团队没有固定公网 IP，且本次明确不增加 Basic Auth；因此该方案只能提供默认流量转移和低可见性的预览入口，不能宣称提供强访问控制。

## 决策

1. 增加一个本地生产部署编排入口。操作员只从本地执行该入口，由它 SSH 到生产主机、以脱离会话的方式启动远端部署、轮询同一任务状态，并执行部署后的只读验收。现有 `deploy/deploy-production.sh` 保留为生产主机内部脚本，不作为本地入口。
2. staging 继续使用 `staging.bytedepth.cn`，但 Nginx 按预览状态分流：
   - 没有预览状态的请求统一 `301` 到 `https://bytedepth.cn`，保留原路径和业务查询参数；
   - 只有严格写成 `?preview=true` 的首次请求建立预览 Cookie，随后访问 staging 内容；
   - `?preview=true` 是路由标记，不是安全凭据。知道该地址的人仍可能访问 staging。
3. 所有 staging 的脚本、E2E、验收命令和知识库示例必须使用 `?preview=true` 的预览入口；不得将不带预览标记的 staging URL 作为可访问地址或测试基址。
4. staging 响应增加 `noindex` 约束；预览 Cookie 使用 `Secure`、`HttpOnly`、`SameSite=Lax` 和有限有效期，并提供显式清除预览状态的方式。

## 后果

**正向**

- 本地操作员不会再把生产主机脚本误当成本地脚本执行。
- 远程部署中断后可以通过同一任务日志继续观察，不会因重试而重复启动同一个 Tag。
- 普通 staging 访客和搜索引擎被 301 引导到生产，团队仍可通过明确的预览入口验收。
- E2E、文档和运维脚本共享同一访问语义，减少域名改了一处、遗漏另一处的问题。

**负向**

- 无 Basic Auth、IP 白名单或 VPN 时，预览入口不是安全边界；参数泄露或被发现后，任何人都可访问 staging。
- staging 域名仍需保留公网 80/443，DNS 和 TLS 不变；只能依靠 Nginx 路由、noindex 和预览状态减少公开流量。
- E2E runner 必须先建立预览 Cookie，脚本契约和 staging 验收会相应增加一步。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| 当前需求是默认流量转生产，而非强访问控制 | 出现未授权访问、数据泄露或必须满足合规访问控制时，升级为 Basic Auth、VPN 或零信任方案 |
| 团队可以在浏览器或测试上下文中保留 Cookie | E2E 或人工验收无法稳定保留 Cookie 时，改为专用 preview 域名或受控访问层 |
| staging 与生产继续共享业务路径结构 | 预览路径与生产路径不一致时，重新设计重定向的 URI 保留规则 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 预览参数被搜索引擎收录或公开传播 | 立即增加认证或 VPN，并重新验收 staging 数据暴露范围 |
| 远程部署编排器无法识别已在运行的 Tag 任务 | 停止自动重试，先读取远端状态；必要时将任务管理迁移到 systemd socket |
