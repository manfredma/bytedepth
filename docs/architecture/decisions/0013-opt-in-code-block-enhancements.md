# ADR-0013: 代码块增强采用显式启用且保持普通代码块兼容

- **状态**: Accepted
- **日期**: 2026-09-22
- **决策者**: 项目所有者

## 上下文

文章正文来自 Markdown，当前由 CommonMark 渲染为标准的
`<pre><code class="language-*">`。现有文章中大量代码块只有语言标记，没有标题、折叠或多语言关系；这些内容必须继续按当前方式展示。

Obsidian 社区插件可以修改 Obsidian 内部的预览 DOM，但插件的运行时 HTML、CSS 和 JavaScript 不会随 Markdown 进入 bytedepth。若把插件输出当成发布格式，会导致插件未安装、插件更换或服务端渲染时出现不一致。

## 决策

bytedepth 自己实现代码块增强组件，但只对 Markdown 中明确声明增强元数据的代码块启用。无增强元数据的普通代码块继续由现有 CommonMark 路径输出，不增加包装元素、工具栏、折叠行为或 Tab 分组。

增强渲染的范围限定为 Markdown 文档顶层的 fenced code block。引用块、列表项等嵌套节点继续走现有 CommonMark 普通代码块渲染，以保持既有行为稳定；如果未来需要增强嵌套代码块，必须单独设计递归渲染和分组边界。

采用以下稳定元数据子集：

- `title:<文本>` 或 `file:<文本>`：显示代码块标题；
- `fold`：允许该代码块以折叠状态展示；
- `tabs:<分组标识>`：只有拥有相同分组标识且连续的代码块才组成多语言 Tab。

示例：

````markdown
```java
// 这是普通代码块，输出保持不变
```

```java title:Example.java tabs:install
...
```

```kotlin title:Example.kt tabs:install
...
```
````

Obsidian 插件只作为可选的编辑端体验参考，不作为 bytedepth 的运行时依赖。bytedepth 不自动合并相邻的普通代码块，也不直接复制 Obsidian 插件生成的 DOM。

放弃以下方案：

- **所有代码块统一增加复制/折叠工具栏**：会改变存量普通代码块的视觉和 DOM 结构，回归风险高。
- **仅按相邻语言代码块自动分组**：无法区分作者想展示两个独立代码块还是想创建多语言 Tab。
- **依赖某一个 Obsidian 插件的渲染结果**：插件升级、禁用或迁移到其他 Markdown 工具后，发布端会失去确定性。
- **首期完整兼容所有插件参数**：插件参数众多且语义不稳定，先维护明确且可测试的最小子集。

## 后果

**正向**

- 存量普通单语言代码块的 HTML、CSS 和交互保持兼容。
- 增强能力由 bytedepth 自己控制，复制、折叠、Tab、移动端和无障碍行为可以统一测试。
- Markdown 文件仍然可在没有插件的环境中阅读；增强元数据不会改变代码正文。
- 将来可以增加新的元数据，但必须显式启用并补充解析、渲染和 E2E 回归。

**负向**

- Obsidian 与 bytedepth 的完整视觉效果不会自动同步，需要分别实现。
- 作者需要显式添加增强元数据，不能依赖相邻代码块自动推断 Tab 关系。
- 首期只兼容 `title`、`file`、`fold` 和 `tabs`，复杂的插件专属参数暂不保证。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| 现有文章中的普通代码块不应因新 UI 统一升级而改变展示 | 项目所有者明确要求所有存量代码块都出现复制按钮或语言标签 |
| 显式元数据足以表达实际的多语言示例 | 作者频繁需要非连续代码块组成 Tab，或需要 Tab 内嵌完整 Markdown |
| bytedepth 与 Obsidian 共享 Markdown 源文本，而不共享渲染 DOM | 导入链路开始持久化并发布插件生成的 HTML |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 普通代码块出现不可接受的布局或交互回归 | 立即关闭普通路径增强，仅保留显式 `tabs` 分组路径，并回滚相关全局样式 |
| 显式 Tab 语法无法表达主要文章场景 | 新建 ADR 评估完整 `tabs` 容器语法，不在本 ADR 中隐式扩展解析器 |
| Obsidian 插件成为唯一稳定的团队写作工具 | 重新评估是否采用插件语法作为发布端兼容标准，并增加版本锁定和迁移测试 |
