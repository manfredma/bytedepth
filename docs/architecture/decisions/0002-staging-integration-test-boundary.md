# ADR-0002: 将跨进程测试固定为 staging 集成测试

- **状态**: Accepted
- **日期**: 2026-09-10
- **决策者**: 项目所有者

## 上下文

现有 Maven Surefire 按文件名执行所有 `*Test`。其中 `RedisRateLimitAdapterTest` 会直接连接独立 Redis，却以普通单测名称存在；因此换一台没有本地 Redis 的开发机就失败。这既违背“断网、单进程可执行才是单测”的约束，也把本机端口和数据状态变成隐式发布依赖。

跨进程 Redis、MySQL、Flyway 和浏览器场景需要真实服务拓扑。staging 是独立且可写的预发环境，适合作为这些测试的唯一执行位置。

## 决策

单元测试只允许断网、无外部进程执行；使用 mock、fake、内存数据库或进程内 Redis 均可。跨进程服务测试统一改名为 `*IT`，由 Maven Failsafe 的 `staging-integration` profile 在 staging 执行；默认 Surefire、变更覆盖率门禁和本机开发命令明确排除它们。E2E 继续仅在 staging 主机运行。

集成 runner 连接 staging 已部署的 native 服务，按 `run_id` 为数据库、缓存、搜索索引和图片资源创建隔离空间。测试不得临时构建或启动服务，也不得发布 staging 服务端口。

跨进程集成测试固定在 staging 执行，避免结果依赖开发机端口和数据状态。缺少构建级隔离的测试分类已造成开发环境失败，因此相关入口由 Maven profile 和契约测试共同固定。

## 后果

**正向**

- 任意无网络的开发机能稳定执行单元与覆盖率门禁。
- 真实服务测试在与部署相同的 staging 主机执行，结果绑定到候选 SHA，且不暴露数据服务端口。
- Maven 生命周期清楚表达测试性质，发布脚本不再误把本地集成失败当作单测失败。

**负向**

- staging 需要维护固定版本的 Maven/Node/浏览器运行时和隔离服务资源。
- 集成测试反馈较慢，开发期须优先以单元测试覆盖业务分支。

## 假设

| 假设 | 可证伪信号（出现时重评） |
|------|--------------------------|
| staging 可提供独立且稳定的 native 测试服务 | 测试资源互相污染或服务健康检查无法满足 runner 契约 |
| 单元测试可通过 fake/mock 覆盖外部服务失败分支 | 某业务分支只能依赖真实服务且无法在 staging 获得确定性数据 |

## 退出条件

| 信号 | 预设行动 |
|------|----------|
| 集成测试数量或时长使单机 staging 成为瓶颈 | 评估专用测试节点或 CI staging runner，但仍保持外部服务测试不在开发机执行 |
