# bytedepth 统一语言（Ubiquitous Language）

本文是项目全局术语的唯一权威入口。它采用领域驱动设计（DDD）的方式，将产品、领域模型、接口、测试和运维中使用的词汇放到明确的**限界上下文**内。需求、界面文案、代码命名和测试描述应使用此处定义；同一个词跨上下文时必须标出上下文，不能凭字面猜测。

> 这是一份业务词典，不是表结构或接口清单。模块依赖与实现约束见[架构概览](overview.md)，路由见[路由一览](routes.md)。

## 1. DDD 共用语言

| 术语 | 在 bytedepth 中的含义 | 约束 |
| --- | --- | --- |
| 领域 | 系统要解决的业务问题集合。 | 本项目不是单一“大博客领域”；至少包含内容、阅读互动、身份授权、参与度、分析、项目展示、搜索和运维上下文。 |
| 限界上下文（Bounded Context） | 一组内部用词一致、模型边界明确的业务能力。 | 跨上下文传递 DTO、标识或领域事件，不把一个上下文的持久化对象直接当作另一个上下文的模型。 |
| 统一语言（Ubiquitous Language） | 业务人员与开发人员共同使用且含义稳定的词汇。 | 产品中文名、代码名不同但语义相同时，必须在本词典明确映射，例如“专栏”与 `Series`。 |
| 实体（Entity） | 依靠稳定身份而非全部属性来区分的对象。 | `Post`、`User`、`Series`、`Category`、`Tag`、`Project`、`Comment`、`PostAnnotation` 都是实体。 |
| 值对象（Value Object） | 依靠值本身表达语义、没有独立生命周期的对象。 | `AnnotationVisibility`、`PostStatus`、`UserStatus`、slug、正文选区偏移、评分统计均应以值语义理解。 |
| 聚合（Aggregate） | 维护业务不变量的一致性边界。 | 同一操作只应修改一个聚合；跨聚合协调用应用层命令或领域事件完成。当前代码未为每个聚合单独实现根类型时，仍按本表定义业务边界。 |
| 聚合根（Aggregate Root） | 聚合对外唯一的修改入口。 | 文章、专栏、用户、分类、标签、项目、文章评论、阅读批注分别作为其业务聚合的根。不得通过另一聚合的内部对象绕过其规则。 |
| 仓储（Repository） | 面向领域的聚合读取、保存和查询抽象。 | domain/app 定义接口或端口，infrastructure 实现；仓储不是 Controller 的数据库捷径。 |
| 命令（Command） | 会改变业务状态的意图。 | 应以 `*CmdExe` 实现；名称使用业务动词，例如“发布文章”“提交评论”“创建阅读批注”。 |
| 查询（Query） | 不改变业务状态、只返回信息的请求。 | 应以 `*QryExe` 实现；分页查询返回 `PageResult` 或等价结果。 |
| 领域事件（Domain Event） | 领域内已经发生、可被其他能力响应的事实。 | 如“文章已被访问”；事件名用过去式，不能把尚未完成的命令叫事件。 |
| DTO | 穿过应用层/适配层的传输视图。 | DTO 不是领域实体，不能承载绕过领域规则的状态变更。 |

## 2. 限界上下文地图

| 上下文 | 职责 | 核心聚合/术语 | 与其他上下文的关系 |
| --- | --- | --- | --- |
| 内容与编排 | 创作、发布和组织可阅读内容。 | 文章、专栏、分类、标签、正文、Slug。 | 向阅读、搜索、参与度和分析提供已发布文章。 |
| 阅读批注 | 对文章正文选区划线、评注及可见范围。 | 阅读批注、划线、评注、选区、创建者。 | 只附着于可阅读文章正文；不等同于文章评论。 |
| 身份与授权 | 注册、账号状态、角色与内容归属。 | 用户、角色、权限、作者、读者、所有权。 | 为内容、评论、批注及后台操作提供身份和授权判定。 |
| 社区参与 | 对整篇文章发表评论和评分。 | 文章评论、评分、评分摘要。 | 评论面向整篇文章；评分面向文章与访客组合。 |
| 访问与阅读分析 | 记录访问、阅读进度并生成统计。 | 访问记录、访问会话、有效阅读、阅读完成度、统计。 | 消费文章访问事实，不改变文章内容。 |
| 搜索与发现 | 为已发布文章建立搜索索引并检索。 | 搜索文档、检索结果、索引。 | 是内容上下文的下游投影，不是文章真相来源。 |
| 项目展示 | 管理独立的作品/项目卡片。 | 项目、技术标签、展示顺序。 | 与文章、标签同属网站内容，但没有文章从属关系。 |
| 运维 | 观察部署与依赖服务状态，发起受控部署请求。 | 运行状态、依赖状态、部署请求。 | 不直接成为内容或用户数据的事实来源。 |

## 3. 内容与编排上下文

| 术语 | 定义 | 关系与边界 | 不要称为 |
| --- | --- | --- | --- |
| 文章（Post） | 可独立创建、编辑、发布、删除和阅读的内容单元；是内容上下文的核心聚合。 | 一篇文章至多属于一个分类、一个专栏；可关联多个标签；有作者与状态。 | 专栏、项目、页面 |
| 正文 | 文章 Markdown 渲染后的可阅读内容区域。 | 阅读批注只定位正文，不含标题、元数据、导航、专栏导航或文章评论区。 | 整篇文章（需要强调定位范围时） |
| 草稿 | 尚未公开的文章状态。 | 不出现在公开阅读、搜索、专栏或批注能力中。 | 未完成文章（领域状态应说“草稿”） |
| 已发布 | 可对外阅读的文章状态。 | 可被索引、进入专栏、被评分、评论、访问统计与阅读批注。 | 上线（讨论领域状态时） |
| 已删除 | 逻辑删除的文章状态。 | 对外不可见；不是物理删除的同义词。 | 草稿、已发布 |
| 专栏 | 围绕同一主题、按阅读顺序组织的一组文章；是产品与界面的规范名称。 | 文章最多加入一个专栏，并拥有专栏内顺序。前台路由为 `/columns`。 | 系列（产品文案中避免） |
| `Series` | 代码、数据模型和部分后台路由对“专栏”的实现名称。 | 与“专栏”是同一业务概念，不是新的内容类型。 | 独立系列功能 |
| 专栏顺序 | 文章在所属专栏中的位置。 | 仅对已加入专栏的文章存在；与创建、发布、全站列表排序无关。 | 全站排序 |
| 分类（Category） | 用于内容归档的树形目录。 | 可有父分类；文章最多归属一个分类。 | 标签、专栏 |
| 标签（Tag） | 描述文章主题、技术或特征的扁平关键词。 | 无父子层级；文章可关联多个标签。 | 分类、全文检索词 |
| Slug | 可公开出现在 URL 中的稳定文本标识。 | 名称变更不必然变更 slug；内部数据库关联使用 ID。 | 标题、名称、ID |
| 推荐（Featured） | 文章是否进入推荐展示位的属性。 | 不改变发布状态、作者、分类或专栏归属。 | 文章状态 |

## 4. 阅读批注上下文

| 术语 | 定义 | 视觉与业务规则 | 不要称为 |
| --- | --- | --- | --- |
| 阅读批注（Post Annotation） | 针对文章正文一段选区的完整记录：**选区 + 划线 + 可选评注 + 可见范围 + 创建者**。 | 是独立聚合，附着于一篇文章，但不是文章评论。 | 全局评论、纯评注 |
| 选区 | 读者本次选中的连续正文文字。 | 以正文 `textContent` 起止偏移与文本快照保存，用于刷新后恢复定位。 | 段落、锚点链接 |
| 划线 | 选区文字下方的线型标记；可以没有评注。 | 正文文字保持原颜色和透明背景；只增加线。现有线型为琥珀波浪、珊瑚直线、绿色虚线、蓝色双线。默认私有；已有划线的选区仍可再次划线。 | 高亮、背景色、评注 |
| 评注 | 附着于某条划线的文字想法。 | 原文处用同色圆角虚线框区分；桌面端点击框左上方的“评注”标签打开侧栏，移动端点击标记查看轻量评注。侧栏以低饱和墨蓝展示，默认公开，可改私有。 | 划线、文章评论 |
| 划线评论 | 阅读页面的能力名称，涵盖选词后的复制、划线和评注。 | 不是“文章评论”的别名。 |
| 阅读批注侧栏 | 聚合展示**带评注**的阅读批注的阅读界面。 | 打开时隐藏阅读工具栏；纯划线不在侧栏中罗列。 | 文章评论区 |
| 公开 | 任何能阅读该文章的访客可见该阅读批注。 | 仅创建者可以编辑或删除。 | 登录用户可见 |
| 私有 / 仅本人可见 | 只有创建者可见的阅读批注。 | 匿名创建者依靠浏览器归属 Cookie；服务端只保存摘要。 | 隐藏、草稿 |
| 创建者 | 创建批注的登录用户或匿名读者。 | 决定私有可见性、编辑和删除权限；不必在公开批注中显示身份。 | 文章作者 |
| 匿名读者 | 未登录但进行阅读互动的访客。 | 用 HttpOnly Cookie 识别归属，不能把 Cookie 原文或可逆标识写入数据。 | 匿名作者（除非未来产品明确要展示） |

## 5. 身份与授权上下文

| 术语 | 定义 | 边界 |
| --- | --- | --- |
| 用户（User） | 可注册、审核、激活、封禁并拥有角色的账号聚合。 | 用户状态决定账号是否可完成相应操作。 |
| 访客 | 当前浏览器会话中的访问主体，可能是匿名读者或登录用户。 | 访客不是数据库用户的同义词。 |
| 作者 | 文章或专栏的内容归属用户。 | 与“批注创建者”“评论者”区分；作者权限受所有权约束。 |
| 所有权 | 当前用户能否管理某篇文章或某个专栏的归属关系。 | `ContentOwnershipGuard` 是此规则的 Web 侧保护之一；不能仅用页面隐藏代替授权。 |
| 角色（Role） | 一组权限的集合。 | 角色不是用户状态，也不是具体一次操作的授权结果。 |
| 权限（Permission） | 可被授权判定的原子能力，例如管理文章或专栏。 | 权限代码是实现标识；需求表述仍需说明具体业务动作。 |
| 待审核 / 已激活 / 已封禁 | 用户的生命周期状态。 | 是账号状态，不是角色；封禁不等于删除用户。 |

## 6. 社区参与上下文

| 术语 | 定义 | 边界 |
| --- | --- | --- |
| 文章评论（Comment） | 位于文章正文末尾、针对整篇文章的讨论消息。 | 与阅读批注的“评注”严格不同；不会产生选区或划线。 |
| 评论者 | 提交文章评论的用户。 | 不是文章作者，也不是批注创建者的统称。 |
| 评分（Rating） | 访客对已发布文章的 1–5 星评价。 | 同一访客对同一文章更新既有评分，而非重复累加。 |
| 评分摘要 | 一篇文章的平均分、评分人数及当前访客评分的查询视图。 | 是派生信息，不是独立评分实体。 |

## 7. 访问与阅读分析上下文

| 术语 | 定义 | 边界 |
| --- | --- | --- |
| 文章访问 | 一次对文章阅读页的有效访问事实。 | 可驱动阅读进度和文章浏览统计；不等于“文章评论”或“评分”。 |
| 页面访问 | 一次对非文章公开页面的访问事实。 | 与文章访问分开统计；例如首页、关于页、项目页。 |
| 访问记录（View Log） | 为分析而保存的一次访问上下文。 | 包含文章/用户、来源、设备、地域、时间等；不是审计日志的泛称。 |
| 访问会话 / 访问令牌 | 标识单次文章访问并关联阅读进度的临时身份。 | 用于幂等上报，不得作为跨文章用户画像标识。 |
| 有效阅读时长 | 页面可见且满足阅读规则时累计的时长。 | 不是单纯的页面停留时长。 |
| 阅读完成度 | 当前访问已阅读正文的比例。 | 与文章字数、评分、发布状态无关。 |
| 统计看板 | 基于访问记录产生的聚合查询界面。 | 是读模型；不得反向直接修改原始访问或内容数据。 |

## 8. 搜索、项目展示与运维上下文

| 术语 | 定义 | 边界 |
| --- | --- | --- |
| 搜索文档（Search Document） | 为全文检索而生成的文章索引投影。 | MeiliSearch 中的索引不是文章真相来源；文章仍以内容仓储为准。 |
| 重建索引 | 以当前已发布文章重新生成搜索投影。 | 是运维/应用命令，不是文章编辑。 |
| 项目（Project） | 独立展示的作品条目，含名称、描述、技术标签、链接和展示顺序。 | 不等同于文章、专栏、分类或文章标签。 |
| 展示顺序 | 项目在项目页的人工排序。 | 与专栏顺序、文章发布时间完全不同。 |
| 运行状态 | 应用、数据库、Redis、搜索等依赖的可用性快照。 | 是观测结果，不是业务领域状态。 |
| 部署请求 | 要求受控部署某个已发布不可变版本的操作意图。 | 不是已经完成的部署事实；部署规则以 `deploy/README.md` 为准。 |

## 9. 用语规则与示例

- 正确：**“给这段正文划一条绿色虚线，再写一条公开评注。”**
- 正确：**“打开阅读批注侧栏，只查看有评注的划线。”**
- 正确：**“把文章加入‘Java 基础’专栏的第 3 篇。”**
- 正确：**“该读者本次文章访问的有效阅读时长为 86 秒。”**
- 错误：**“给文字加一个绿色评注背景。”** 应明确为“绿色虚线划线”；背景高亮当前不是能力。
- 错误：**“在评论区查看所有评注。”** 应区分文章评论区与阅读批注侧栏。
- 错误：**“系列和专栏分别怎么管理？”** 当前是同一概念；产品讨论说“专栏”，代码讨论可说 `Series`。
- 错误：**“封禁管理员角色。”** 应区分“封禁用户”（状态）与“调整角色/权限”（授权）。

## 10. 演进约束

1. 引入新概念前，先确认它属于哪个限界上下文、是否是既有概念的别名，并更新本文。
2. 新增划线线型必须保持正文文字颜色和背景不变；如要新增背景高亮，必须以“高亮”作为独立概念、独立菜单项和独立数据语义。
3. 跨上下文的功能描述必须使用上文统一语言；例如“发布文章后重建搜索索引”，而不是笼统说“更新文章到搜索”。
4. 产品文案统一使用“专栏”；`Series` 仅用于代码和数据库实现讨论。
5. 本文与代码不一致时，先核实当前业务规则；确认变更后必须同步修改代码或本文，不能保留两个真相来源。
