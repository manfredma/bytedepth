# 前端设计语言

本文件定义 bytedepth 面向读者页面的稳定视觉与交互基线。所有新增或改造前端页面、组件、视觉样式与交互前，开发者和编程 Agent 都必须先阅读本文件；具体组件实现仍须遵守 [前端组件约束](../agent-guides/frontend-components.md) 与 [前端公共组件模式](../engineering/frontend-patterns.md)。

## 设计定位

bytedepth 的界面应像一份现代技术出版物：专业、安静、以阅读和思考为中心。它不是后台管理系统，也不是强调即时互动的社交评论区。

设计目标是让正文始终是视觉主角；导航、工具、批注和操作控件只在需要时提供清晰帮助，不与内容争夺注意力。

## 核心原则

1. **克制优先。** 优先用留白、位置、细线和大小差异建立层级，不用大字号、重字重、大面积色块或装饰性阴影制造“设计感”。
2. **阅读优先。** 正文的可读性高于操作效率的视觉表达；辅助内容应更轻、更小、更安静。
3. **颜色表达语义。** 颜色只能用于有稳定含义的状态、分类或风险等级。相同语义在所有相关元素中使用同一种颜色，不把品牌蓝当作通用强调色。
4. **紧凑但不拥挤。** 去除重复标题、无意义说明和多余分隔线；保留足够的点击面积、可读行距和可扫描的信息分组。
5. **稳定而低干扰。** 页面、侧栏与正文构成一个阅读整体。滚动、展开和悬浮不应产生弹跳、脱离或抢夺视线的感觉。
6. **统一优于局部创新。** 相同任务使用相同布局、文案和控件；编辑态应尽量复用新建态，而不是再设计一套局部表单。

## 排版与信息层级

- 使用跨平台稳定的通用字体栈；不得依赖 IDE、操作系统或本地环境特有字体，避免乱码和平台差异。
- 正文保持页面中最大的阅读权重。辅助信息使用更小字号、常规字重与较低对比度；不要以大量粗体代替层级设计。
- 书籍式内容（如阅读评注）可使用较小的衬线字体栈，例如 `Georgia, "Songti SC", "SimSun", serif`；它必须由组件自身声明，不能影响正文或其他组件。
- 时间、可见范围、作者等元信息应作为次级信息自然流动排列，不应抢占标题或操作的空间。
- 横线只用于表达明确的边界或语义标记。它应细、短且贴近关联文字；避免把每个区块都框成卡片或加上下两条分隔线。

## 色彩与分类

颜色必须先有语义，后有装饰。阅读评注的既定分类如下：

| 类型 | 颜色 | 用途 |
| --- | --- | --- |
| 补充说明 | 蓝色 | 背景知识、补充解释 |
| 重点摘录 | 黄色 | 值得记住的原文或观点 |
| 实践结论 | 绿色 | 可执行的方法、经验或结论 |
| 疑问待办 | 红色 | 未解决问题、风险或后续行动 |

- 类型文字本身、关联划线、左侧标记线与细横线使用该类型颜色，形成一致的视觉语言。
- 下拉列表中的每个候选项也应以其实际代表的颜色呈现，不能全部显示为同一种强调色。
- 红色只用于风险、删除和待处理事项；删除按钮应可识别但保持克制，避免大面积警告式视觉。

## 阅读评注模式

评注是文章旁的“书页批注”，不是另一篇正文或评论区。

- 评注正文比文章正文更小、常规字重、较舒展但紧凑的行高；不使用醒目的粗体。
- 被引用的划线文字下方只保留一条与评注类型一致的极细横线，紧贴引用文字；不在评注正文下方再增加对称横线。
- 左侧竖线应继承评注类型颜色，用于快速扫描分类。
- 页脚采用流式布局：左侧依次呈现类型、可见范围、创建时间；编辑、删除等操作按钮靠右。窄侧栏也应保持清晰而非堆成多层表单。
- 新建和编辑必须使用相同的编辑器布局：评注类型、可见范围、取消和保存共用紧凑操作行。新建使用侧栏底部编辑器；编辑已有评注时，编辑器必须在该评注卡片的原位置展开，不能弹出或跳转到另一张编辑卡片。取消或保存后，原位置恢复为评注卡片。
- 删除仅对本人可见，并在实际删除前提供一次简洁确认；确认文案清楚说明动作，不制造额外恐吓感。

## 布局、滚动与动效

- 固定侧栏和正文必须在同一个阅读坐标感中工作；禁止依靠页面 overscroll、夸张位移或独立漂浮效果制造层次。
- 动效仅用于说明状态变化（打开、关闭、选中、保存反馈），时长短、幅度小，可被立即打断。
- 页面滚动时，侧栏不应因橡皮筋或容器错位而显得与正文脱离；必要时在根页面抑制纵向 overscroll。
- 操作反馈优先使用原位状态、轻微颜色变化或简短文本，不使用干扰阅读的全屏提示。

## 组件实施约束

- 每个组件必须有自己的命名空间、字体、字号、间距和默认变量；不得依赖 `body`、`*`、裸 class 或其他组件的继承样式。
- 组件之间除布局位置外不得互相影响。新增样式前应确认选择器不会覆盖文章、导航或无关页面。
- 优先复用现有公共组件与交互模式；若要新增视觉语言，先在本文件补充稳定规则，再在组件中实现。
- 任何风险操作都应确认权限边界，并提供必要确认；普通操作不要过度确认。

## 主题变量

前台颜色与字体通过一组 `--bd-*` CSS 变量定义于 `static/css/theme.css`，涵盖背景、表面、文本、边框、强调色、导航和代码块等。新增或改造前台样式应复用这些变量，不要硬编码颜色；需要新语义色时先在主题文件补齐变量再使用。

- 主题切换只改变颜色、边框、阴影和代码块质感，不改页面布局、导航结构、内容密度和交互路径。
- 主题偏好存于浏览器 `localStorage`（键 `bytedepth.theme`），不向服务端发请求，不影响缓存、SEO 和登录状态；`localStorage` 不可用时静默回退默认主题。
- 主题切换仅覆盖前台公共页面，后台 `admin/**` 不纳入主题切换。

## 开发前检查清单

开始前端工作前，逐项确认：

- [ ] 该页面或组件是否让阅读内容保持为视觉主角？
- [ ] 层级是否主要由留白、位置、细线和字号建立，而不是粗体或大色块？
- [ ] 使用的颜色是否有明确语义，并在同一语义的所有元素中保持一致？
- [ ] 新建、编辑、展示态的布局与操作是否统一？
- [ ] 元信息是否紧凑、可扫描，并在窄宽度下保持流式布局？
- [ ] 动效、滚动和侧栏是否稳定、低干扰，不会造成视觉脱离？
- [ ] 字体是否跨平台稳定，组件样式是否完全自隔离？
- [ ] 删除、权限等风险交互是否既安全又不过度打扰？

若设计与本文件冲突，应先明确说明冲突原因并更新本文件或获得项目所有者确认；不得静默偏离。
